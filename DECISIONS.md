# DECISIONS.md

One line per non-obvious choice, and why. Newest at the bottom.

- **Repo lives in `tessera-quest/`, sibling to the existing `tessera/` repo, not inside it.** The two are different hackathon projects that happen to share a name (PLAN.md §3 A1/A7) — merging them would tangle two unrelated git histories.
- **Git remote set to `https://github.com/ramkirangaruda/Gamified-E-Learning-Platform.git`** (user-provided). Go module path matches it (`github.com/ramkirangaruda/Gamified-E-Learning-Platform`) so internal import paths won't need to change if this ever needs to resolve as a real Go module.
- **AST validator is hand-written Go (packages/ast/ast.go, validate.go), not a JSON-Schema-library-driven one.** `schema.json` still exists as the documented contract (and future TS/ajv use if M2 wants it), but the Go side doesn't load it at runtime — keeps M1 at exactly one new dependency (PLAN.md §3 A2).
- **`net/http`'s stdlib `ServeMux` (Go 1.22+ method+path patterns) instead of a router package.** No third-party router is named in brief §4, and the stdlib mux is enough for three routes.
- **AST depth semantics:** the top-level `program` array is depth 1; each compound node's `body`/`then`/`else` array is one deeper than the array containing it. Depth 4 is the deepest array allowed to *exist*, checked at the moment that array would be constructed — an empty array one level too deep still fails, not just a non-empty one. Documented in `packages/ast/fixtures/README.md`.
- **Executor's `error_signature` is scoped to what pure execution can determine: `infinite_loop`, `empty_program`, `unknown_call`.** The other 8 signatures in brief §11's taxonomy (`missing_turn`, `off_by_one_repeat`, …) require comparing an attempt's shape against a level's intended solution — that's the M3 hint-lookup layer's job, not the executor's.
- **Grid coordinate convention (not specified by the brief): row-major, up = y-1, down = y+1, right = x+1, left = x-1.** Internal to `internal/executor`; a future grid renderer just needs to match it.
- **Tick budget is checked *before* incrementing, not after.** Charging then checking let `TicksUsed` report 501 against a 500 budget (caught by `TestTickBudgetNeverHangs` during M1) — checking first guarantees `TicksUsed` never exceeds `TickBudget`.
- **SQLite: `PRAGMA synchronous=FULL`, default rollback journal (not WAL), single `sql.DB` connection.** WAL leaves persistent `-wal`/`-shm` sidecar files, which fights the write-then-rename + `backup.db`-copy recovery scheme brief §7 requires for M4 hot-yank testing — a rollback journal only exists transiently mid-transaction, so `pet.db` stays a single self-contained file the rest of the time. `synchronous=FULL` is relied on as the actual fsync mechanism rather than a manual `os.File` fsync, since modernc.org/sqlite is a transpilation of the real engine (not a reimplementation) and genuinely issues the platform fsync/FlushFileBuffers call.
- **M1's executor grid is a hardcoded 8x8 wall-free stand-in** (`internal/api/api.go: defaultGrid`), since `content/levels/` (M2) doesn't exist yet. `/api/program` takes a raw AST body only; level-aware grid selection replaces this in M2.
- **`/api/state` shape:** `GET` returns `{learner, pet, inventory}` (creating defaults on a fresh/empty `pet.db`), `POST` upserts learner+pet fields by the drive's one existing row (brief §1: the drive *is* the account, so there's never more than one learner per `pet.db`). Provisional — will grow once M2's UI defines what it needs (PLAN.md §3 A4).
- **Binary is named `launcher.exe`/`launcher` at build time (`-o` flag), not by renaming the `cmd/server` source directory.** The Go package is accurately named for what it is (an HTTP server); the drive-layout filename brief §7 wants is a packaging decision, applied at build time.
- **2026-08-14 — Windows/Linux launcher cross-compiled ahead of M4, at the user's explicit direction** (M1 was otherwise complete and passing). `CGO_ENABLED=0 GOOS=windows|linux GOARCH=amd64 go build` — clean on both, confirming the pure-Go SQLite bet from brief §4 pays off exactly as intended. Smoke-tested `bin/win/launcher.exe` natively on this dev machine (it happens to be Windows) as a sanity check, but per the user's instruction this is **not** a substitute for their own acceptance test on real target hardware at M4 — that milestone's acceptance criterion still requires their sign-off, not mine.
- **`llama-server.exe` fetched prebuilt from `ggml-org/llama.cpp` release `b10430`, `win-cpu-x64` asset** — CPU-only deliberately, since brief §14 flags "demo machine unknown" and a GPU can't be assumed. Bundled with every DLL in the release archive rather than hand-trimming the true dependency chain (safer against a missing-DLL failure discovered on stage; revisit if drive space gets tight). Smoke-tested with `--version`.
- **Built/fetched binaries (`bin/win/`, `bin/linux/`, `llama-server.exe` + DLLs, future `models/*.gguf`) are gitignored, not committed.** Reproduced instead via `scripts/build-launchers.{ps1,sh}` and `scripts/fetch-llama-server.{ps1,sh}` (the latter pinned to `b10430`, not "latest," so a re-run months from now doesn't silently drift). Keeps the repo itself free of ~75MB+ of binary blobs; the actual drive assembly (M4) is what needs the binaries physically present, not the git history. `bin/linux/llama-server` (for the Pi 5 hub) isn't fetched yet — nobody's asked for it and the brief doesn't need it until M3/M5.
- **2026-08-14 — `.sh` equivalents of both scripts added** (the Pi 5 hub is Linux and has no PowerShell to run the `.ps1` versions). Same pinned asset/tag, `curl`+`unzip` instead of `Invoke-WebRequest`+`Expand-Archive`; the Windows-only post-fetch `--version` smoke check is dropped since a Windows PE binary can't execute on Linux to run it.
- **`fetch-llama-server` requires internet, which is a real tension with the offline-at-the-event premise (brief §13's router-unplugged assumption) — documented in `scripts/README.md` rather than silently left as a gotcha.** It's a prep/dev-time convenience; the actual thing that ships to the venue is an offline copy of both platform binaries kept on a spare drive, refreshed via this script ahead of time, never depended on at the event itself.
- **Known gap, flagged not fixed: `build-launchers` only targets `linux/amd64`, but the Pi 5 hub is `arm64`.** `bin/linux/launcher` as built today won't run on the actual hub hardware. Left alone for now — fixing it wasn't in scope for "add `.sh` equivalents of the existing scripts," and Hub Mode (M5) is the first milestone that actually needs it — but noted here so it surfaces before M5, not during it.
- **2026-08-15 — M2 started with the card visuals first, ahead of the grid renderer, per explicit direction: the 14 Blockly block screenshots go straight to print and printing/laminating has real lead time.** Frontend scaffolded in `web/` (Vite+React+TS+Tailwind+Blockly, per brief §4), builds into `../app` (the drive layout target). `cards.html`/`CardGallery.tsx` is a second, dev-only Vite entry point alongside the real game — not linked from the game UI, exists purely to render and export the 14 cards.
- **The 14 Blockly block definitions ARE the print cards, so they're flat stack blocks — no Blockly-native C-shaped/mutator nesting.** A physical card can't visually contain other cards, so `repeat`/`if`/`while` are separate open+close block pairs (`card_repeat_4` + `card_end_repeat`, etc.), exactly mirroring brief §6's card vocabulary. This means the `blocks` source's AST compiler can reuse the exact same open/close stack-parser the `cards` (camera) source needs — one compiler, not two — and it means a child can make the identical "forgot to close it" mistake on-screen as on the desk, so the brief's "unbalanced open/close is a normal event, not an error" hint-handling design applies uniformly to both input surfaces. Logged as the single biggest M2 architecture call; flag if this reading of "the Blockly definitions produce the card screenshots" was wrong.
- **Card colour is grouped by control-flow family, not just "a colour per card": blue (movement), amber (repeat open/close), green (if/else/end-if), purple (while/end-while).** Same-family open/close pairs share a colour so a repeat's end-card is visually distinct from a while's end-card before any validation ever runs — cuts down the single most common child mistake (brief §6) at the source instead of only handling it after the fact via hints.
- **Card export: rasterize each block's own SVG client-side (canvas + `toBlob`) rather than relying on OS-level screenshots.** Three non-obvious fixes were needed to get a faithful render (all documented inline in `web/src/exportCard.ts`): the grid background's `fill: var(--blocklyGridPattern)` references a custom property defined on the injectionDiv wrapper *outside* the cloned `<svg>`, so it resolves to invalid and paints solid black — removed the element entirely, since a print card doesn't want Blockly's dot-grid background anyway. Blockly's actual stylesheets live in `<head>`, not inline in the SVG, so a cloned SVG rendered standalone has no styling at all until those rules are inlined into an embedded `<style>`. And the font rule is scoped `.geras-renderer.classic-theme .blocklyText` with both classes living on that same outside-the-clone wrapper, so the export was silently falling back to a browser-default serif font until those two classes were added directly onto the cloned `<svg>` root. All three fixes are permanent, in-app (`web/src/exportCard.ts` + the gallery's "Export all 14 cards" button), not one-off script hacks — reproducible by anyone who edits a card's text/colour later.
- **Exported cards are gitignored** (`print/cards/*.png`) — same reasoning as the other binary/generated-asset gitignore entries: regenerable from source (open `cards.html`, click "Export all 14 cards"), not worth versioning as binary blobs. `web/` itself (the actual source) is of course committed.
- **2026-08-15 — Real Home Mode editor built (`web/src/Editor.tsx`), with indent guides (`web/src/blocks/indentGuides.ts`) for the flat card blocks.** Two non-obvious bugs found and fixed via direct empirical testing (constructing block chains through the live Blockly API in a running browser, not just reasoning about it): (1) connected next-blocks nest in the DOM — each block's `<g>` contains its next block's `<g>` as a child — so a block's transform is relative to its *immediate predecessor*, not the workspace origin; writing absolute `depth*INDENT_PX` as every block's own transform-x double-counts past depth 1. Fixed by writing only the delta versus the previous block in the chain. This also means Blockly's own `getRelativeToSurfaceXY()` stops being trustworthy for X once the transform's been overwritten (it reflects Blockly's internal model, not the live DOM) — absolute X for guide-line placement is now tracked by accumulating deltas ourselves from the untouched top block. (2) `block.getHeightWidth().height` is not a block's own height — for a nested block it's the cumulative height of that block *plus* everything connected below it — so `top.y + top.height` way overshot "bottom of the opener." Fixed by using the next block in the chain's own Y instead, since stack blocks sit Y-adjacent with zero gap by construction.
- **Added the unmatched-opener warning affordance** (queue item 2 extension): any opener left on the analysis stack at the end of its chain gets a dashed amber outline (`.quest-unmatched-open`), not a hard error style — consistent with brief §6's "unbalanced is a normal event, a teaching moment."
- **Known gap, not yet resolved: real drag-and-drop snap detection near an indented block hasn't been empirically tested.** The indent correction only touches the SVG transform, not Blockly's internal connection-position tracking, so a *new* block dropped near an already-indented block's connector snaps against the connector's untouched logical position, which can differ from its visual position by up to one indent step (20px) per depth level. Not fixed — deep surgery into Blockly's connection system is disproportionate for a cosmetic affordance, and the discrepancy is within normal mouse-drop imprecision for a child dragging chunky blocks. Flagged rather than silently shipped; revisit if playtesting shows it actually causing missed connections.
- **2026-08-15 — ArUco print pipeline: all 14 composited, detection-tested green, A4 sheet(s) generated.** `scripts/compose-card.py` refactored into an importable `compose_card()`/`save_card_png()` pair (dash in the filename means `importlib.util` loads it by path, not a normal `import`) so `compose-all-cards.py` and `test-detect-cards.py` share the exact compositing logic rather than a second hand-copied version drifting out of sync. Card id is parsed from the filename the web gallery already produces (`card-<NN>-<slug>.png`) rather than a second hardcoded id table. `test-detect-cards.py` is the acceptance gate per instruction — ran it, all 14 pass (`cv2.aruco` decodes every composited card back to its expected id).
- **"Single A4 sheet with all 14" is geometrically impossible and wasn't forced.** 14 cards at the spec'd 9x5cm = 630 cm² of card area; one A4 sheet is 21x29.7cm = 623.7 cm² total, smaller than the raw card area alone before any cut margin. Shrinking the cards to fit one sheet was rejected — 3.5cm is what the marker was sized for, and print pipeline discussion earlier (`scripts/compose-card.py`) treats the physical marker size as a detection-reliability parameter, not a cosmetic one. `scripts/make-print-sheet.py` instead lays out as many as fit per A4 portrait page (2 cols x 5 rows = 10/page, the better-fitting orientation vs. landscape's 3x3=9) and spills onto additional pages — 14 cards becomes a 2-page PDF. Logged in `QUESTIONS.md` in case a smaller physical card size is preferred after all.
- **Pillow added as a Python dependency, tooling-only.** Needed for the print-sheet PDF export specifically — OpenCV composites images but has no PDF writer; Pillow's `Image.save(..., save_all=True, append_images=[...])` does multi-page PDF in one call. Everything else in the print pipeline stays cv2-only. Not part of the shipped Pi/laptop runtime. Flagged in `QUESTIONS.md` since it's a real (if small) dependency addition, not something brief §4 pre-approved.
- **Print outputs gitignored** (`print/composited/`, `print/*.pdf`) — same reproducible-from-source reasoning as everything else generated (`print/cards/`, `bin/`, `app/`). Sent directly to the user as files instead (test card earlier, full batch + PDF now) so the actual deliverable doesn't depend on them being in git.
